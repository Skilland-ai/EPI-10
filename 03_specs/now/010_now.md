# 010_now - EPI10 Healthie UI Discovery Sprint

## Status

- Opened on 2026-07-12; paused as execution focus on 2026-09-15.
- Spec `011_now.md` is now the single active execution spec. Outstanding
  Healthie discovery criteria remain pending; this change does not close them.
- Specs `001_now.md` through `009_now.md` are historical/closed inputs, even

- This spec does not enable Stage 06 or authorize implementation.

## Objective

Execute a UI-led discovery of Healthie using the test case
`EPI10-TEST-001` to determine what Healthie can support for EPI10 in practice,
what depends on plan/add-ons, what should remain in Odoo, and what must be
validated later through API discovery.

The discovery must record observed evidence. It must not infer product
capabilities from the target journey or treat unverified UI options as available.

## Scope

In scope:

1. Healthie account/workspace, internal users, roles and permissions.
2. Branding and client entry experience.
3. Test client and client profile using only fictitious data.
4. Forms, intake flows, consents and questionnaires.
5. Documents, demo laboratory PDF and demo final report.
6. Secure communication, emails and notifications.
7. Appointments and calendar as a candidate capability.
8. Tags, groups, tasks and workflows as lightweight helpers.
9. Payments, packages, labs, programs, goals and metrics as lateral/future
   capabilities.
10. End-to-end replay of `EPI10-TEST-001` and handoff to API discovery.

## Boundaries

- Odoo remains the operational center for case states, tasks and ownership.
- Do not recreate the complete EPI10 operation in Healthie.
- Do not use real personal, health or genetic data.
- Use a Raul-controlled test identity and an email different from the provider
  login for `EPI10-TEST-001`.
- Do not promise automated TellmeGen integration.
- A plan/add-on restriction is a finding, not a product defect.
- Separate UI observation from assumptions and API questions.
- Do not treat lateral capabilities as Fase 1 scope without an explicit later
  decision.
- Do not generate an implementation backlog or Stage 06 plan.

## Evidence Standard

For every explored block, capture:

- result: `Verified`, `Partial`, `Blocked` or `Unknown`;
- actor/view: admin, Aitor-like internal user or client;
- navigation path and configuration tested;
- screenshot or other reproducible evidence when permitted;
- data created or changed in the demo account;
- plan/add-on dependency if shown;
- implication for EPI10 Fase 1;
- Odoo boundary;
- question for Healthie, EPI10 or API discovery;
- cleanup action if applicable.

## Unknowns

- Healthie account access and Raul-controlled test email.
- Current Healthie plan, add-ons and permissions.
- Availability of a safe demo/sandbox environment.
- Ability to inspect both internal and client views.
- Restrictions on screenshots or exported evidence.
- Sprint calendar, daily capacity and target completion date.

## Risks

- Mistaking a plan restriction for absence of a capability.
- Treating visible UI as proof of API availability.
- Over-configuring Healthie and duplicating Odoo responsibilities.
- Introducing real or sensitive data into a discovery environment.
- Allowing attractive lateral features to expand Fase 1 scope.
- Leaving demo users, documents or notifications active after testing.
